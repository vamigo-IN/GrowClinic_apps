# Database migration — MySQL (×4) → PostgreSQL (one database)

Scope: GrowClinic, Audit, GMB and Engine move from four separate MySQL/MariaDB
databases to **one PostgreSQL 17 database, `growclinic`**, with one schema per
application. This document records what existed, what was built, every type
decision, and how data is moved and validated. **Nothing here has touched a
production database**; all testing used local fixtures.

---

## 1. Current MySQL schema overview

| App | Source DB (Hostinger) | How the schema was managed | Tables |
|---|---|---|---|
| GrowClinic | `u109…_growclinic` | Prisma 6.3.1 `db push` (no migrations; `prisma_output.txt` shows a push that proposed a full reset) | User, Lead, Post, Tag, `_PostToTag`, ContactMessage, ConsultationBooking, Project, ClinicAudit, Testimonial, SiteSettings |
| Audit | `u109…_audit` | `CREATE TABLE IF NOT EXISTS` + ~40 swallowed `ALTER TABLE ADD COLUMN` **at every boot** (`db.js`) | leads, settings, chat_sessions, admin_sessions, admin_login_attempts, admin_users, popup_leads, admin_logs, api_usage, lead_tasks, lead_events, raw_events, automation_rules, automation_runs, failed_crm_events, xp_ledger, checkins, notification_prefs |
| GMB | `u109…_gmb` | `db/schema.sql` executed at every boot + an ad-hoc `ALTER TABLE locations` | users, organizations, memberships, otp_codes, sessions, locations, google_connections, health_scores, location_issues, reviews, content_drafts, qr_assets, subscriptions, invoices, public_audits, audit_events |
| Engine | `engine` (own MySQL 8 container) | Prisma 5.22 `db push` on every container start | Clinic, ActivationKey, User, Lead (+ enums Plan, ClinicStatus, UserRole, LeadStatus) |

Reference copies of the MySQL-era DDL (used by the importer and its fixture test):
`database/import/fixtures/mysql/{growclinic,engine}.sql` (generated from the
original Prisma schemas), `apps/audit/db/mysql-legacy/schema.sql` (reconstructed
from the original `db.js`, final column set), `apps/gmb/db/mysql-legacy/`.

MySQL features in use that needed attention: `AUTO_INCREMENT`, `TINYINT`/
`TINYINT(1)` flags, `MEDIUMTEXT`/`LONGTEXT`, `ENUM`, `DATETIME`/`DATETIME(3)`,
`DEFAULT/ON UPDATE CURRENT_TIMESTAMP`, `JSON`, `DECIMAL`, `ENGINE=InnoDB`,
`utf8mb4_*_ci` collations (case-insensitive comparisons and uniqueness),
`ON DUPLICATE KEY UPDATE`, `INSERT … insertId`, `affectedRows`, `?`/`:name`
placeholders, `IN (?)` array expansion, `SUM(boolean_expr)`, `INTERVAL ? DAY`,
`DATE_SUB`, `CURDATE()`, `TIMESTAMP(CURDATE(), …)`, `DATE_FORMAT(…'%x-W%v')`,
`IFNULL`, `UPDATE … ORDER BY … LIMIT`, and mysql2 `dateStrings: true`.

## 2. PostgreSQL target schema

```
database growclinic   (UTF8, C.UTF-8, timezone UTC)
├── core         core.schema_migrations  (migration ledger: scope, version, sha256, applied_at)
├── growclinic   11 Prisma tables + _prisma_migrations          owner growclinic_owner
│                citext extension lives here
├── audit        18 tables                                      owner audit_owner
├── gmb          16 tables + set_updated_at() trigger function  owner gmb_owner
└── engine       4 tables + 4 enum types + _prisma_migrations   owner engine_owner
```

Sources of truth:
- `database/migrations/core/0001_platform_schemas.sql`
- `database/migrations/audit/0001_init.sql`
- `database/migrations/gmb/0001_init.sql`
- `apps/growclinic/prisma/migrations/20260917000000_init_postgresql/`
- `apps/engine/prisma/migrations/20260917000000_init_postgresql/`
- `database/privileges/*.sql` (grant overrides)

Roles: `<app>_owner` (NOLOGIN, owns everything in its schema) and `<app>_app`
(LOGIN, DML only, connection-limited) — see ARCHITECTURE.md §6.

Table/column **names are unchanged** (camelCase columns stay camelCase, quoted in
SQL) so application row objects keep exactly the same keys.

## 3. MySQL → PostgreSQL type conversions

Decisions were made per application after reading how each value is used —
not by a blanket mapping.

| MySQL | PostgreSQL | Where | Reasoning |
|---|---|---|---|
| `INT AUTO_INCREMENT PRIMARY KEY` | `integer GENERATED BY DEFAULT AS IDENTITY` | audit | *BY DEFAULT* lets the import keep original ids; sequences are advanced past the max id afterwards. |
| `TINYINT` / `TINYINT(1)` 0/1 flags | **`smallint CHECK (col IN (0,1))`** | audit | The CRM API, n8n/Sheets webhooks, admin UI and code (`active === 0`, `SUM(verified = 1)`) exchange 0/1. BOOLEAN would change the JSON contract seen by external consumers. |
| `TINYINT(1)` | **`boolean`** | gmb | Only ever read with `!!`; not exposed as 0/1 anywhere. |
| Prisma `Boolean` | `boolean` | growclinic, engine | Prisma-native. |
| `TINYINT` (rating 1–5) | `smallint` | gmb.reviews | numeric. |
| `MEDIUMTEXT` / `LONGTEXT` / `TEXT` | `text` | all | PostgreSQL `text` has no size tiers. |
| JSON stored in `MEDIUMTEXT` (crmRemarks, crmAiSummary, conditions/actions, payload) | **`text`** (not jsonb) | audit | The code `JSON.parse()`s these strings; jsonb would hand it objects. |
| `JSON` | `jsonb` | gmb | pg returns parsed JSON exactly like mysql2 did. |
| `DATETIME` | `timestamptz(0)` | audit | Session TZ pinned to UTC; a pg type parser returns `'YYYY-MM-DD HH:MM:SS'` strings exactly as mysql2 `dateStrings: true` did. |
| `DATETIME(3)` | `timestamptz(3)` | gmb | Returned as `Date`, as before. |
| Prisma `DateTime` | `timestamp(3)` (Prisma default, UTC) | growclinic, engine | Prisma convention; values are UTC on both sides. |
| `DATE` | `date` (returned as `'YYYY-MM-DD'`) | audit | |
| `BIGINT` epoch-ms (`expiresAt`, `inviteExpires`) | `bigint` → JS number | audit | Parser maps int8 to Number (safe below 2⁵³), as mysql2 did. |
| `COUNT(*)`, `SUM(int)` | int8/numeric → JS number | audit, gmb | mysql2 returned numbers for COUNT; code already wraps SUMs in `Number()`. |
| `DECIMAL(p,s)` | `numeric(p,s)`, returned as string | gmb | mysql2 also returned strings. |
| `ENUM(...)` | **`varchar + CHECK`** | gmb | Evolving prototype: a CHECK changes with a normal migration; native enums need `ALTER TYPE` and can't drop values. |
| Prisma `enum` | native PostgreSQL enum | engine | Prisma-managed. |
| `CHAR(36)` UUID ids | **`varchar(36)`** (not `uuid`) | gmb | Ids come from URLs; `uuid` would turn a malformed id into a 500 (cast error) instead of the existing 404. Verified. |
| `VARCHAR(n)` the app truncates or controls | `varchar(n)` | audit, gmb | Keeps the length guard. |
| `VARCHAR(n)` receiving **untruncated** user/AI/webhook/Google text (clinicName, city, campaign, gclid, referrer, profile fields, public_audits, audit_events.targetId…) | **`text`** | audit, gmb | PostgreSQL always rejects over-long values; a lost-tracking-write regression was more likely than any benefit. |
| Prisma `String` (`VARCHAR(191)`) | `text` | growclinic, engine | Prisma default. |
| `utf8mb4_*_ci` on identity columns (login email, slugs, tag names) | **`citext`** | growclinic | Admin login with a differently-cased email, case variants of slugs, and `connectOrCreate` on a differently-cased tag name (which would otherwise hit the slug unique index → HTTP 500) keep behaving as on MySQL. Verified. |
| `_ci` in admin search (`contains`) | Prisma `mode: "insensitive"` | growclinic | `ILIKE`. |
| `_ci` in search / username | `ILIKE`; unique index on `lower(username)` + `lower()` lookup | audit | |
| `DEFAULT CURRENT_TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | all | |
| `ON UPDATE CURRENT_TIMESTAMP(3)` | `BEFORE UPDATE` trigger `set_updated_at()` | gmb (8 tables), audit.notification_prefs | Verified (location `updatedAt` changes on PATCH). |
| `ENGINE=InnoDB`, `CHARSET utf8mb4` | — | — | Database is UTF-8; emoji/Devanagari verified end-to-end. |

### SQL semantics changed in application code
| MySQL | PostgreSQL | App |
|---|---|---|
| `?` placeholders | kept in source, converted to `$n` by `query()` (quote-aware) | audit |
| `:name` placeholders | kept, converted by `q/one/exec` (quote- and `::cast`-aware) | gmb |
| `ON DUPLICATE KEY UPDATE x = VALUES(x)` | `ON CONFLICT (…) DO UPDATE SET x = EXCLUDED.x` | audit (settings, chat_sessions, checkins, notification_prefs) |
| `result.insertId` / `affectedRows` | `RETURNING id` / `rowCount` (same return shape kept) | audit |
| `SUM(col = 1)` | `COUNT(*) FILTER (WHERE col = 1)` | audit |
| `NOW() - INTERVAL ? DAY` | `NOW() - (?::int * INTERVAL '1 day')` | audit |
| `DATE(x) = CURDATE()` | `x::date = CURRENT_DATE` | audit |
| `TIMESTAMP(CURDATE(), '23:59:59')` | `CURRENT_DATE + TIME '23:59:59'` | audit |
| `DATE_FORMAT(x,'%Y-%m' / '%x-W%v')`, `DATE(x)` buckets | `to_char(x,'YYYY-MM' / 'IYYY-"W"IW' / 'YYYY-MM-DD')` | audit |
| `IN (?)` with an array | `= ANY(?::text[])` | audit |
| unquoted camelCase aliases | quoted (`AS "reportViewed"`) so row keys keep their case | audit, gmb |
| `NOW() - INTERVAL 1 HOUR` | `NOW() - INTERVAL '1 hour'` | gmb |
| `IFNULL` | `COALESCE` | gmb |
| `UPDATE … ORDER BY … LIMIT 1` | `UPDATE … WHERE id = (SELECT id … ORDER BY … LIMIT 1)` | gmb |

## 4. Shared entities — analysis and decision

| Concept | GrowClinic | Audit | GMB | Engine | Same meaning? |
|---|---|---|---|---|---|
| **User** | CMS admins (NextAuth, bcrypt) | CRM staff (scrypt, 7 roles, TOTP) | clinic customers (WhatsApp OTP, phone identity) | clinic owners/staff + PLATFORM | **No** — four different populations and auth models. |
| **Lead** | website form prospect (B2B) | `chat_sessions` = the CRM record; `leads` legacy log; `popup_leads` soft leads | `public_audits` (prospect searched a business) | **patient** lead owned by a clinic tenant | **No.** Engine leads are a tenant's patients — merging them with GrowClinic's own prospects would break tenant isolation. The three B2B prospect stores overlap conceptually but differ in shape, lifecycle and dedupe rules. |
| **Clinic** | Project (case study, free text) / ClinicAudit.clinicName (free text) | clinicName (free text) | organizations + locations (paying tenants) | Clinic (paying tenant) | Partly (a real clinic may be a GMB org *and* an Engine tenant), but there is **no shared key** today. |
| Sessions, settings, integrations, audit logs | JWT | admin_sessions, settings | sessions, audit_events | — | App-private. |

**Decision:** no `core.users`, `core.leads` or `core.clinics` were created. The
models do not share meaning or keys, and unifying them would require business
logic rewrites (dedupe, merge, ownership) that are out of scope and risky. The
`core` schema holds only genuine platform infrastructure (the migration ledger).

**Recommended future step (additive, no behaviour change):** a `core.clinics`
registry with *nullable* link columns (`gmb.organizations."coreClinicId"`,
`engine."Clinic"."coreClinicId"`), populated by an explicit matching process,
and a read-only reporting view over prospect leads — both once the business
defines what "the same clinic" means.

## 5. Application-specific entities

Everything listed in §1, each in its own schema, owned by its owner role and
reachable only by its runtime role. Notable handling:
- **audit.settings** stores integration secrets (API keys, SMTP, TOTP secret) —
  import them; they override env values at runtime.
- **gmb.google_connections** stores AES-GCM–encrypted OAuth tokens — they only
  decrypt with the same `TOKEN_ENC_KEY`/`JWT_SECRET` (or the old built-in
  fallback if neither was set).
- **engine."User".passwordHash** — see §12.

## 6. Relationships

- **Within schemas only.** No cross-schema foreign keys (no shared entities).
- **gmb:** the original MySQL foreign keys, 1:1 (CASCADE on org/location/user deletion).
- **engine / growclinic:** Prisma relations as before (`Post.authorId` RESTRICT; implicit m:n `_PostToTag` CASCADE; Engine children CASCADE on Clinic).
- **audit (new):** the implicit relations became real foreign keys, created
  **NOT VALID** — enforced for every new write, while legacy orphan rows are
  preserved on import and reported instead of blocking it:
  - `chat_sessions.ownerId → admin_users` ON DELETE SET NULL
  - `admin_sessions.userId → admin_users` ON DELETE CASCADE
  - `xp_ledger.userId`, `checkins.userId`, `notification_prefs.userId → admin_users` ON DELETE CASCADE
  - `automation_runs.ruleId → automation_rules` ON DELETE SET NULL
- **audit soft references (intentionally no FK):** `lead_tasks`, `lead_events`,
  `raw_events`, `api_usage`, `popup_leads`, `automation_runs.sessionId → chat_sessions`.
  They are written by fire-and-forget paths that can race the chat-session
  insert, and history rows have always outlived a deleted lead.
- `import validate --validate-constraints` turns the NOT VALID constraints into
  validated ones once any orphans are resolved.

## 7. Migration order

**Schema (every environment):** `migrate` job → roles → `core/0001` (schemas,
citext, grants) → `audit/0001` → `gmb/0001` → Prisma growclinic → Prisma engine →
ownership + grants. Idempotent; verified re-run changes nothing.

**Data (one-off, per environment):**
1. Stop writes to the old apps (maintenance window).
2. `mysqldump` each source database (+ `SELECT @@global.time_zone, @@system_time_zone, NOW(), UTC_TIMESTAMP();`).
3. Fresh PostgreSQL volume → `./scripts/migrate.sh apply` (**before** any app starts — the apps seed rows at boot and the importer refuses non-empty tables).
4. Load dumps into the throwaway `import-mysql` source → `import import` → `import validate`.
5. Copy files: GrowClinic uploads → `growclinic_uploads`; Audit `reports/`, `leads.json` → `audit_data`.
6. Start apps → smoke test → switch traffic.

Table order inside each app follows dependencies (e.g. users → organizations →
memberships → locations → children), although the import session also defers
FK checks (`session_replication_role = replica`).

## 8. Data import strategy

Tooling: `database/import/` (`import.mjs`, Dockerfile) + `compose.import.yml`.

- **Source:** a throwaway `mysql:8.4` container on the private network, datadir
  on tmpfs, loading `database/import/dumps/<app>.dump.sql` (restored copies —
  never the live server). Without dumps it loads the bundled fixtures.
- **Target:** the migrated PostgreSQL schema; the importer never creates,
  alters or drops anything.
- Columns are matched by name. A source column with no target column aborts
  that app (data would be lost); target-only columns get their defaults and
  are reported.
- Values are converted according to the **target** column type (§3): 0/1 →
  boolean where the target is boolean; `0000-00-00…` → NULL (counted and
  reported); naive `DATETIME` + an explicit source offset → timestamptz
  (`IMPORT_AUDIT_SOURCE_TZ`, `IMPORT_GMB_SOURCE_TZ`; Prisma apps are UTC);
  JSON → jsonb; BIGINT as exact strings; varchar overflow aborts with the
  column name.
- One transaction per application: all-or-nothing. Primary keys preserved;
  identity sequences set past the imported maximum.
- Refuses tables that already contain rows (no silent duplication).
- mysql2 exists only in this one-off tool, never in an application image.

## 9. Validation strategy

1. `import validate`: per table, **row count and a SHA-256 digest of all primary
   keys** on both sides must match.
2. Relationship check per known parent/child pair (orphan counts), including the
   soft references.
3. NOT VALID constraint report / optional validation.
4. Value spot checks (types, precision, time zones, UTF-8) — see TESTING.md.
5. Application level: data-layer regression test (`tests/audit-db.test.js`,
   19 groups) and the end-to-end suite (`scripts/smoke-test.sh`, 127 checks)
   against the migrated database, plus manual login/admin review of real data.

**Fixture run (2026-09-17):** 4 apps, 49 tables, all counts and key digests
matched; the planted zero-date became NULL; both planted legacy orphans
(`xp_ledger` → deleted user, `lead_events` → deleted lead) were preserved and
reported; re-import was refused; Audit reads of imported rows returned the
original shapes; new ids continued after the imported maximum; Engine's legacy
SHA-256 admin hash was upgraded to scrypt by the seed with the correct password
and left untouched with a wrong one.

## 10. Rollback strategy

- **Before cut-over** nothing changes on the old side: the MySQL databases and
  Hostinger apps stay untouched (read-only dumps only), so rollback = keep
  serving from them.
- **Failed import:** the app's transaction rolls back automatically; fix and
  re-run on a fresh volume (or drop and re-migrate the scratch database).
- **After cut-over, within the maintenance window:** point DNS/VPS Nginx back
  at the old apps. Writes made on the new platform in that window must be
  reconciled manually — keep the window short and read-only if possible.
- **Later:** restore the PostgreSQL backup taken immediately before cut-over
  (`scripts/restore.sh <dir> --replace-live`). There is no automated
  PostgreSQL → MySQL export; the old MySQL dumps remain the fallback of record
  until the platform has run cleanly for an agreed period (e.g. 30 days).
- Schema migrations are forward-only; a bad migration is fixed with a new one
  or by restoring the pre-migration backup.

## 11. Production migration considerations

- **Time zones:** run the time-zone query on each source first. Prisma apps are
  UTC; Audit/GMB `CURRENT_TIMESTAMP` columns follow the MySQL server zone while
  JS-written columns (e.g. `crmFollowUpAt`) are UTC. If the server was not UTC,
  those columns need per-column conversion — do not import blindly.
- **Case-insensitive duplicates:** MySQL `_ci` prevented them in unique columns,
  but check `lower()` duplicates in GrowClinic `User.email`/`Tag.name`/slugs
  before import anyway (citext unique indexes would reject them).
- **Zero dates / invalid JSON / over-long values** abort or are reported by the
  importer — review the output, never add `--allow-non-empty` to "get past" it.
- **Secrets:** import `audit.settings` (it holds live integration keys and the
  admin TOTP secret). Keep GMB's `TOKEN_ENC_KEY`/`JWT_SECRET` exactly as in the
  old environment or stored Google tokens become undecryptable (users would
  just reconnect Google).
- **Files are not in the database:** copy GrowClinic uploads (`UPLOAD_DIR` or
  `public/uploads`) and Audit `reports/`, `leads.json`, `.admin-password`.
- **Engine** previously ran `prisma db push` against its own MySQL; confirm its
  live schema matches the Prisma schema before dumping.
- **GrowClinic `prisma_output.txt`** shows a `db push` that wanted to reset the
  production DB — never run `db push`/`migrate reset` against any database again.
- **Downtime:** plan a write freeze (maintenance mode: Audit has one built in),
  lower DNS TTLs in advance, and keep the MySQL dumps and old apps until sign-off.
- **Post-import:** `ANALYZE`, `import validate --validate-constraints` after
  resolving orphans, first backup, then open traffic.

## 12. Engine password hashing

The Engine seed stored `passwordHash = sha256(password)` — unsalted, fast,
rainbow-table-able. **Not preserved.** `apps/engine/src/lib/password.ts`:

- New hashes: **scrypt** (N=2¹⁵, r=8, p=1, 16-byte random salt, 64-byte key) via
  Node's built-in crypto — no new dependency; stored as
  `scrypt$N$r$p$salt$hash` so parameters can be raised later.
- `verifyPassword()` still accepts legacy 64-hex SHA-256 hashes and returns
  `{ ok, needsRehash: true }` — nobody is locked out.
- Upgrade paths: (a) `engine-seed` with the correct `ADMIN_PASSWORD` rehashes a
  legacy platform admin (never resets on mismatch — verified), (b) the future
  login route **must** call `verifyPassword` and store `hashPassword()` when
  `needsRehash` is true.
- No login route exists in the supplied Engine code yet, so no current user flow
  is affected. Emails are normalised to lower case (PostgreSQL comparisons are
  case-sensitive).
